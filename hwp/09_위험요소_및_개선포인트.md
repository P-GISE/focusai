# 09. 위험요소 및 개선포인트

기준 경로: `focusai-webapp`  
갱신일: 2026-05-19

이 문서는 현재 코드 기준으로 운영 전에 확인해야 할 위험요소와 개선 우선순위를 정리한다.

## 최근 반영된 개선

- `deploy/prod.env.example`에는 실제 비밀값 대신 placeholder만 남기도록 정리했다.
- `npm test` 대표 명령은 서버 API 테스트, Discord 봇 회귀 테스트, 문서성 테스트를 모두 실행한다.
- GitLab CI verify 단계는 현재 `npm ci`, `npm run lint`를 실행한다.
- 배포 전 로컬 필수 검증 명령은 `npm run lint`, `npm test`, `npm run build`로 문서화되어 있다.
- DB와 uploads 볼륨을 한 묶음으로 백업/복구 테스트하는 운영 절차를 문서화했다.
- `AUTO_MIGRATE_SCHEMA` 운영 사용 기준과 DDL 권한 최소화 전환 절차를 문서화했다.
- 주요 시크릿 회전 절차와 데이터 보존 정책을 문서화했다.
- FocusAI 전용 Discord 봇은 인프로세스 방식으로 서버와 함께 실행되며, 관리 API와 동일한 서비스 계층을 사용한다.
- FocusAI Discord 봇의 슬래시 명령은 `focus상태`, `focus요약`, `문의목록`, `문의상세`, `문의처리`, `사용자조회`, `최근세션`, `감사로그`, `공지등록`, `공지목록`, `공지수정`, `공지종료`, `알림채널설정`, `알림채널목록`으로 정리되어 있다.
- Discord 봇 설정 저장용 `DISCORD_BOT_SETTINGS_SECRET`이 도입되어 알림 채널 설정 파일을 암호화할 수 있다.
- Discord 봇 명령 등록, 지원 문의 처리, 알림 채널 저장, 공지 명령 파싱에 대한 회귀 테스트가 추가되어 있다.
- `README.md`와 상위 문서는 실제 코드 구조, 환경 변수, API, 운영 방식 기준으로 재정리되었다.
- 카메라 얼굴 중심/크기 추적과 `focusTracking.ts` 안정화 레이어를 추가해 짧은 고개 회전, 필기 자세, 순간 얼굴 미감지를 바로 자리비움으로 확정하지 않도록 했다.
- 학습 화면에 트래킹 안정성, 기준선 상태, 판정 근거 카드를 표시한다.
- 로그인 화면이 API 서버와 MariaDB 헬스체크 실패를 표시하고, 서버가 복구되면 약 5초 간격 재시도로 `/api/bootstrap`을 다시 호출하도록 했다.
- 로컬 dev/preview 클라이언트를 기본 `0.0.0.0` 바인딩으로 바꿔 같은 네트워크의 모바일 브라우저에서 UI와 API proxy를 확인할 수 있게 했다.
- 모바일 뷰포트 `390x844`에서 빌드 로그인 화면, `/api/health`, `/api/bootstrap`, 공지 API 응답, 브라우저 콘솔 오류 0개를 확인했다.
- CSP에 Google Fonts 허용 출처를 추가해 배포 화면의 폰트 로딩 콘솔 오류를 제거했다.
- 로그인/회원가입/비밀번호 입력에 autocomplete 속성을 추가해 모바일 브라우저 입력 품질을 보강했다.
- Capacitor Android 프로젝트를 추가해 현재 웹앱을 Android APK로 패키징할 수 있는 구조를 만들었다.
- Android 매니페스트에 카메라 권한과 FocusAI 앱 아이콘을 반영했고, Android 전용 웹 빌드와 sync 명령을 추가했다.
- Vite dev dependency 취약점은 6.4.2 업데이트 후 `npm audit` 취약점 0개 상태로 확인했다.
- Android SDK를 `D:\tmp\android-sdk`에 설치하고 `npm run android:apk`로 debug APK를 산출했다.
- 공유용 APK 산출물은 `focusai-webapp/apk-packages/`에 local debug APK, server debug APK, zip 묶음으로 정리되어 있다.

## 보안 위험

### 비밀값 관리

- `.env`, `deploy/prod.env.example`, 배포 서버의 환경 파일에 실제 키가 포함되지 않도록 관리해야 한다.
- 과거 커밋이나 배포 파일에 실제 토큰, DB 비밀번호, SMTP 비밀번호가 남아 있었다면 즉시 회전해야 한다.
- Discord 봇 토큰, OpenAI API 키, SMTP 계정, JWT 시크릿, Discord 설정 암호화 시크릿은 같은 저장소나 로그에 노출되면 안 된다.

개선 방향:

- 예시 파일에는 더미 값만 유지한다.
- 배포 환경의 시크릿은 서버 환경 변수나 별도 시크릿 저장소로 관리한다.
- 시크릿 유출 여부를 배포 전 점검 절차에 포함한다.

### 인증과 세션

- 백엔드는 JWT 쿠키와 Bearer 토큰을 모두 지원한다.
- 프로덕션에서는 `SESSION_COOKIE_SECURE=true`, `TRUST_PROXY=true`, HTTPS 프록시 구성이 맞아야 쿠키 보안 속성이 정상 동작한다.
- 관리자 권한은 `ADMIN_EMAILS`, `ADMIN_USER_IDS`, DB의 사용자 역할을 조합해서 판단한다.
- 마지막 관리자 계정 강등 또는 삭제 방지 로직은 존재하지만 운영 중 직접 DB 변경으로 우회될 수 있다.

개선 방향:

- 운영 계정 변경은 애플리케이션 API로만 수행한다.
- 관리자 변경 이벤트를 주기적으로 감사한다.
- 관리자 명령 실행 결과를 별도 알림 채널로 보낼지 검토한다.

### Discord 관리 명령

- FocusAI Discord 봇 명령은 운영 데이터를 조회하거나 변경할 수 있다.
- 명령 실행 권한은 `DISCORD_BOT_ADMIN_USER_IDS`와 `DISCORD_BOT_ADMIN_ROLE_IDS`를 기준으로 제한된다.
- `공지등록`, `공지수정`, `공지종료`, `문의처리`, `알림채널설정`은 실제 운영 상태를 변경한다.

개선 방향:

- 운영 서버에서 관리자 Discord 사용자와 역할 ID를 명시적으로 설정한다.
- 명령어 권한 설정을 Discord 서버 권한과 애플리케이션 내부 권한 양쪽에서 확인한다.
- 변경 명령은 감사 로그와 Discord 알림으로 추적한다.

### Rate limit

- 현재 rate limit은 주로 메모리 기반이다.
- 다중 인스턴스 배포에서는 인스턴스별로 제한이 분산되어 전체 제한이 약해질 수 있다.

개선 방향:

- 다중 인스턴스 운영 시 Redis 같은 공유 저장소 기반 rate limit으로 전환한다.
- 로그인, 비밀번호 재설정, AI 분석, 관리자 변경 API는 더 엄격한 제한을 적용한다.

## 운영 위험

### DB 스키마 자동 보정

- `AUTO_MIGRATE_SCHEMA=true`이면 서버 시작 시 MariaDB 스키마 보정 로직이 실행된다.
- 운영 DB 계정에 DDL 권한이 필요하며, 다중 인스턴스 시작 시 동시 마이그레이션 위험이 있다.
- 현재 MVP 운영은 `AUTO_MIGRATE_SCHEMA=true`를 허용하되, 운영 규모가 커지면 별도 마이그레이션 후 앱 런타임 DDL 권한을 제거하는 절차로 전환한다.

개선 방향:

- 운영에서는 배포 전 마이그레이션 단계를 별도로 실행하고, 앱 런타임의 DDL 권한은 최소화한다.
- `db/schema.sql`과 `ensureSchema` 계열 로직의 차이를 정기적으로 비교한다.

### 업로드 파일

- 프로필 사진과 게시판 첨부 파일은 `UPLOAD_DIR` 하위에 저장된다.
- Docker Compose 기준으로 업로드 볼륨은 `/app/uploads`에 마운트된다.
- DB만 백업하면 첨부 파일과 프로필 이미지가 유실될 수 있다.
- 운영 절차는 DB dump, uploads archive, `.env` secret 백업을 같은 시점의 한 묶음으로 관리한다.

개선 방향:

- DB 백업과 업로드 볼륨 백업을 하나의 운영 절차로 묶는다.
- 복구 테스트에서 업로드 URL 접근까지 확인한다.

### Discord 설정 파일

- FocusAI 봇 알림 채널 설정은 `DISCORD_BOT_SETTINGS_PATH`에 저장된다.
- 이 파일은 서버 재시작 후에도 유지되어야 하며, Docker 환경에서는 볼륨으로 보존해야 한다.

개선 방향:

- 설정 파일 경로가 영구 볼륨에 있는지 확인한다.
- 파일 손상 시 빈 설정으로 복구되는지 점검한다.
- 장기적으로는 DB 테이블로 이전하는 방안을 검토한다.

### CI 검증 범위

- GitLab CI verify 단계는 현재 `npm ci`, `npm run lint`를 실행한다.
- `npm test`는 서버 API 테스트, Discord 봇 회귀 테스트, 문서성 테스트를 모두 포함하지만 현재 CI verify에는 연결되어 있지 않다.

개선 방향:

- 운영 Discord 서버에서 실제 slash command 14개를 실행하는 수동 검증은 배포 후 체크리스트로 유지한다.
- CI verify에 `npm test`와 `npm run build`를 다시 포함할지 결정한다.
- 프런트엔드 브라우저 실패 시나리오는 자동화 또는 수동 검증 항목으로 별도 보강한다.

### 로컬 개발 서버 분리

- 개발 환경에서는 Vite dev server(`5173`)와 Express API server(`8787`)가 분리되어 있다.
- `dev:client`만 켜져 있으면 로그인 화면이 `/api/health` proxy 실패를 감지해 서비스 서버 연결 실패 안내를 표시한다.
- 서버가 늦게 켜지는 경우 클라이언트는 자동 재시도를 수행하지만, 장기적으로는 개발자 경험을 위해 `dev:all` 또는 실행 상태 점검 스크립트를 우선 사용해야 한다.
- dev/preview 클라이언트는 모바일 로컬 확인을 위해 기본 `0.0.0.0`에 바인딩한다. 같은 네트워크의 다른 기기에서 접속 가능하므로 공용 네트워크에서는 주의가 필요하다.

개선 방향:

- 로컬 점검 문서에 `/api/health`, `/api/bootstrap` 확인 명령을 유지한다.
- dev server 시작 실패 또는 Discord 봇 외부 연결 실패가 웹 API 기동 상태와 혼동되지 않도록 로그를 분리한다.
- 필요하면 `dev:web`처럼 클라이언트와 API만 실행하고 봇 자동 시작은 제외하는 스크립트를 추가한다.
- 공용 네트워크에서 작업할 때는 `FOCUSAI_CLIENT_HOST=127.0.0.1`로 바인딩을 제한한다.

### Android APK 빌드와 배포

- Android APK는 Capacitor로 생성한 `android/` 프로젝트에 의존한다.
- 실제 APK 빌드는 Android Studio 또는 Android SDK와 SDK 경로 설정이 필요하다.
- 현재 로컬 PC에서는 `D:\tmp\android-sdk`를 `android/local.properties`로 연결해 debug APK 빌드가 가능하다.
- `apk-packages/focusai-local-debug.apk`와 `apk-packages/focusai-server-debug.apk`는 전달용 debug APK이며, zip 묶음도 함께 보관된다.
- 작업 경로에 한글이 포함되어 있어 Windows Gradle 빌드를 위해 `android.overridePathCheck=true`가 설정되어 있다.
- debug APK는 테스트용이며, 스토어 배포에는 서명된 Android App Bundle과 keystore 관리가 필요하다.
- APK는 Android 전용이므로 iPhone 배포는 Xcode, IPA/TestFlight, App Store 절차가 별도로 필요하다.

개선 방향:

- 실기기 Android에 `apk-packages/focusai-local-debug.apk`와 `apk-packages/focusai-server-debug.apk`를 설치해 운영 배포용 API 주소와 HTTPS 인증서 상태를 검증한다.
- release signing config와 keystore 보관 절차를 문서화한다.
- 스토어 등록 전에는 `npm run android:aab`와 Android App Bundle 서명 절차를 추가한다.

## 데이터 위험

### 계약 타입 중복

- 프런트엔드와 백엔드가 `src/lib/contracts.ts`, `server/src/contracts.ts` 형태로 유사한 타입을 각각 갖고 있다.
- API 응답 형태가 바뀔 때 한쪽만 수정될 위험이 있다.

개선 방향:

- 공용 계약 패키지나 코드 생성 방식으로 단일 원천을 만든다.
- 변경이 잦은 응답은 테스트에서 실제 JSON shape를 검증한다.

### 계정 삭제와 연쇄 삭제

- 사용자 삭제 시 세션, AI 분석, 지원 문의, 감사 로그 등 관련 데이터가 함께 정리된다.
- 운영 또는 법적 요구사항에 따라 감사 로그와 문의 이력은 즉시 삭제하면 안 될 수 있다.
- 현재 문서 정책은 서비스 기능 데이터는 계정 삭제 시 삭제하고, 관리자 감사 로그는 보안 감사 목적상 익명화 우선으로 검토한다.

개선 방향:

- 개인정보 삭제와 운영 감사 보존 정책을 분리한다.
- 계정 삭제는 hard delete 대신 익명화 또는 비활성화 모델을 검토한다.

### AI 사용량 추정

- AI 사용량은 `ai_usage`에 저장되고, 비용은 추정치로 계산된다.
- 실제 과금액과 차이가 날 수 있다.

개선 방향:

- 사용 모델과 가격표 변경 시 비용 계산 로직을 함께 갱신한다.
- 월별 예산 경고와 관리자 알림을 추가한다.

## 코드 구조 위험

### 대형 프런트엔드 파일

- `src/App.tsx`가 화면, 상태, 핸들러, 라우팅 역할을 크게 담당한다.
- 변경 범위가 넓어지면 회귀 위험이 커진다.

개선 방향:

- 화면 단위 컴포넌트와 도메인 훅으로 점진적으로 분리한다.
- 관리자, 세션, 게시판, 인증 영역을 먼저 분리한다.

### 대형 백엔드 저장소 계층

- `server/src/store.ts`는 여러 도메인의 데이터 접근을 한 파일에서 담당한다.
- 기능 추가 시 충돌과 회귀 가능성이 높다.

개선 방향:

- 사용자, 세션, 문의, 공지, 감사 로그, AI 사용량 저장소를 모듈로 분리한다.
- 분리 과정에서 기존 API 응답은 변경하지 않는다.

### Discord 봇 로직

- FocusAI 관리 봇과 Lost Ark 봇이 같은 서버 프로세스 안에 존재한다.
- Discord API 장애나 봇 초기화 실패가 웹 서버 시작 경험에 영향을 줄 수 있다.
- 기존 상위 `디스코드 봇/` 중복 복사본은 프로젝트 밖 백업 위치로 이동했다.
- 백업에는 `.env`, 로그, 데이터 파일이 포함될 수 있으므로 값은 문서화하지 않고 배포 대상과도 분리해서 관리해야 한다.

개선 방향:

- 봇 실패가 웹 API 전체 장애로 번지지 않도록 실패 격리를 유지한다.
- 운영 규모가 커지면 봇 워커를 별도 프로세스로 분리한다.
- 상위 별도 봇 폴더가 실제 운영 대상인지, 과거 백업/임시 자료인지 구분하고 필요하면 별도 저장소나 백업 위치로 분리한다.

## 기능 위험

### 이메일 인증

- 회원가입과 비밀번호 재설정 메일 발송 기능은 있지만, 회원가입 이메일 인증 흐름은 아직 완전한 필수 단계로 보이지 않는다.

개선 방향:

- 이메일 인증 토큰 테이블과 인증 완료 상태를 명확히 분리한다.
- 미인증 사용자의 주요 기능 접근 정책을 정한다.

### 카메라와 브라우저 호환성

- 프런트엔드는 MediaPipe와 브라우저 카메라 권한에 의존한다.
- 모바일 브라우저, 구형 브라우저, HTTPS가 아닌 환경에서 동작 차이가 생길 수 있다.
- 트래킹 안정화 레이어가 오탐을 줄이지만 실제 카메라 각도, 조명, 필기 자세, 모바일 성능에서는 임계값 재검증이 필요하다.
- 로컬 LAN HTTP에서는 모바일 UI/API 확인은 가능하지만, 카메라 권한은 HTTPS 보안 컨텍스트 정책 때문에 차단될 수 있다.

개선 방향:

- 카메라 권한 실패, 모델 로딩 실패, HTTPS 미사용 상태에 대한 사용자 흐름을 보강한다.
- 핵심 브라우저와 대표 디바이스별 수동 검증 체크리스트를 운영 문서에 추가한다.
- 체크리스트에는 짧은 고개 회전, 필기 자세, 3초 내 얼굴 미감지, 6초 이상 얼굴 미감지, 조명 변화를 포함한다.
- 필요하면 기준선 수집 시간과 이탈 확정 임계값을 설정화한다.

### PDF 리포트

- 클라이언트에서 세션 리포트 PDF를 생성한다.
- 긴 세션, 이미지 포함, 모바일 환경에서 성능 문제가 발생할 수 있다.

개선 방향:

- 대용량 세션 데이터의 PDF 생성 시간을 측정한다.
- 필요하면 서버 사이드 리포트 생성이나 요약 리포트를 별도로 제공한다.
