# 05. 업무 플로우

## 1. 회원가입과 로그인

1. 사용자가 이메일, 이름, 비밀번호로 회원가입합니다.
2. 서버는 비밀번호 정책을 검증하고 비밀번호를 해시합니다.
3. `users`, `user_settings` 기본 데이터가 생성됩니다.
4. 서버는 인증 세션 토큰을 만들고 DB에는 토큰 해시만 저장합니다.
5. 브라우저에는 HttpOnly 쿠키가 설정됩니다.
6. 클라이언트는 `GET /api/bootstrap`으로 초기 상태를 불러옵니다.
7. 로그인 화면은 먼저 `/api/health`로 API와 MariaDB 상태를 확인합니다.
8. API 서버가 늦게 켜졌거나 일시적으로 끊긴 경우 `서비스 서버에 연결할 수 없습니다.` 안내를 표시하고 약 5초 간격으로 헬스체크를 재시도합니다.
9. 헬스체크가 복구되면 다시 `/api/bootstrap`을 호출해 로그인 상태 또는 로그인 화면을 갱신합니다.

관리자 권한은 `ADMIN_EMAILS` allowlist와 DB의 `is_admin` 정책에 따라 결정됩니다.

## 2. 동의 갱신

1. 서버가 요구하는 동의 버전과 사용자 동의 버전이 다르면 클라이언트가 동의 화면을 표시합니다.
2. 사용자가 개인정보/카메라 동의를 수락합니다.
3. `POST /api/account/consent`가 호출됩니다.
4. `users.privacy_consent_at`, `users.camera_consent_at`, `users.consent_version`이 갱신됩니다.

## 3. 학습 세션

1. 사용자가 과목, 학습 시간, 모드를 선택합니다.
2. 클라이언트가 `LiveSession` 상태를 생성합니다.
3. 진행 중 세션은 `localStorage`의 `focusai:web:session-draft`에 주기적으로 저장됩니다.
4. 1초 단위로 시간, 집중 상태, 화면 상태, 탭 전환, 유휴 상태를 기록합니다.
5. MediaPipe 분석이 가능하면 얼굴/프레이밍/시선/머리 방향/눈 깜박임/얼굴 중심/얼굴 크기를 보조 신호로 사용합니다.
6. `focusTracking`은 개인 기준선과 지속 시간 기준으로 순간 감지값을 안정화해 짧은 고개 회전, 필기 자세, 일시적인 얼굴 미감지를 바로 이탈로 확정하지 않습니다.
7. 학습 화면 오른쪽 카드에는 트래킹 안정성, 기준선 상태, 판정 근거를 표시합니다.
8. 일정 간격으로 안정화된 집중 점수 타임라인을 누적합니다.
9. 목표 시간이 끝나거나 사용자가 종료하면 `POST /api/sessions`로 저장합니다.
10. 서버는 `study_sessions`, `session_score_samples`, `session_events`를 트랜잭션으로 저장합니다.
11. 저장 성공 후 session draft를 제거합니다.
12. 결과 화면에서 사용자가 세션 메모를 수정하면 `PATCH /api/sessions/:sessionId/notes`를 호출합니다.

## 4. AI 피드백

1. 사용자가 AI 피드백 화면을 엽니다.
2. 클라이언트가 `GET /api/ai/feedback`을 호출합니다.
3. 서버가 사용자의 세션과 설정을 불러옵니다.
4. Anthropic API가 활성화되어 있으면 일일 요청 수와 예상 비용을 검사합니다.
5. 허용 범위 안이면 Claude API를 호출합니다.
6. 실패하거나 비활성화되어 있으면 로컬 분석(`server/src/insights.ts`)으로 fallback합니다.
7. 사용량과 차단 여부는 `ai_usage_logs`에 기록됩니다.

## 5. 비밀번호 재설정

1. 사용자가 이메일을 입력해 비밀번호 재설정을 요청합니다.
2. 서버는 계정 존재 여부와 무관하게 동일한 성공 응답을 반환합니다.
3. 계정이 존재하면 토큰을 생성하고 DB에는 해시만 저장합니다.
4. SMTP 설정이 있으면 reset 링크를 이메일로 보냅니다.
5. 사용자가 링크의 token으로 새 비밀번호를 저장합니다.
6. 토큰이 만료되었거나 이미 사용되었으면 실패합니다.

## 6. 공지

관리자:

1. 관리자 페이지 또는 Discord 명령으로 공지를 등록합니다.
2. 공지 제목, 내용, 유형, 고정 여부, 활성 여부, 시작/종료 시각을 저장합니다.
3. 서버는 관리자 감사 로그를 남깁니다.

사용자:

1. 클라이언트가 활성 공지와 공지 목록을 조회합니다.
2. 활성, 기간, 고정 여부에 맞는 공지를 화면에 표시합니다.

## 7. 문의/신고

사용자:

1. 문의 유형, 제목, 내용을 입력합니다.
2. `POST /api/support/tickets`로 문의를 접수합니다.
3. 내 문의 목록에서 상태와 관리자 답변을 확인합니다.

관리자:

1. 관리자 페이지 또는 Discord 명령으로 문의 목록을 확인합니다.
2. 문의 상세를 보고 상태와 답변을 변경합니다.
3. 변경 내역은 감사 로그에 기록됩니다.

## 8. 관리자 대시보드

1. 관리자가 로그인합니다.
2. 서버는 `requireAdmin`으로 관리자 여부를 검증합니다.
3. 클라이언트가 `GET /api/admin/overview`를 호출합니다.
4. 서버는 사용자/세션/공지/문의/감사 로그/시스템 상태를 취합합니다.
5. 관리자는 공지, 문의, 사용자 권한, Discord 봇 설정을 조작합니다.

## 9. FocusAI Discord 봇

1. 관리자가 관리자 페이지에서 Bot token, Client ID, Guild ID, 채널/역할 제한을 저장합니다.
2. 서버는 토큰을 암호화하여 `discord_bot_settings`에 저장합니다.
3. 관리자가 시작 버튼을 누르면 `createDiscordJsBotGateway()`가 in-process 봇을 시작합니다.
4. `registerCommands=true`이면 Discord slash command를 등록합니다.
5. 봇은 문의 polling, health polling, 일일 요약 interval을 시작합니다.
6. Discord 명령은 guild/channel/role guard를 통과한 뒤 실행됩니다.
7. 서버 재시작 시 `enabled=true`인 봇은 자동 시작됩니다.

## 10. Lost Ark Discord 봇

1. 관리자가 Lost Ark 봇 설정을 저장합니다.
2. 서버는 `createProcessDiscordBotGateway()`를 통해 별도 Node 프로세스를 실행합니다.
3. 기본 작업 디렉터리는 `lostark-discord-bot`입니다.
4. 운영 번들 모드에서는 `uploads/lostark-discord-bot`에 데이터 파일을 보존하면서 실행합니다.
5. 봇 프로세스가 시작 직후 종료되면 관리자 화면에 오류 상태가 저장됩니다.

## 11. 운영 배포

1. `main` 브랜치에 push합니다.
2. GitLab CI verify 단계에서 `npm ci`, `npm run lint`를 실행합니다.
3. 배포 전 로컬 필수 검증으로 `npm run lint`, `npm test`, `npm run build`를 실행합니다.
3. main 배포 단계에서 `/data1/docker/focusai`에 소스를 동기화합니다.
4. 운영 `.env`를 보존합니다.
5. `docker compose build`, `docker compose up -d`를 실행합니다.
6. 컨테이너 상태와 최근 로그를 확인합니다.
